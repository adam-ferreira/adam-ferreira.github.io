01

QA Automation Engineer (mobile Flutter) — BETCLIC

Mars 2026 - Aujourd'hui (Freelance)

Betclic reconstruit son app mobile iOS et Android en Flutter. J'y automatise les tests des fonctionnalités de gamification : missions et défis, classements, jeux de récompense et boosts proposés au moment du pari. Les tests vivent dans un repo partagé entre le mobile et le web.

Construire l'automatisation en même temps que l'app

À mon arrivée, l'app et ses fonctionnalités de gamification étaient en construction. Les tests devaient suivre chaque livraison sans ralentir les devs.

  • Des test IDs dans le code de l'app. Sur mobile, un locator basé sur le texte affiché casse à chaque traduction ou changement de maquette. Je pose moi-même les semantics dans le code Flutter, selon des règles définies avec les tech leads.
  • Des test IDs dans les animations. Les animations interactives sont produites par l'équipe motion design dans un outil dédié, et les tests n'avaient pas accès à leur contenu. J'ai écrit un outil qui ajoute les test IDs dans les fichiers d'animation, vérifié le résultat avec le runtime Flutter, et produit une version que le designer ouvre dans son propre outil pour refaire la modification lui-même.
  • Des données de test créées par API. Une mission de paris demande des paris placés puis réglés. Je les crée par API avant chaque scénario, sur un compte de test dédié. L'UI ne sert qu'à ce que le test vérifie : les tests restent courts et indépendants les uns des autres.
  • Une nightly sur cinq marchés réglementés. Chaque pays a ses règles, ses contenus et ses comptes. Chaque matin, je trie les échecs : bug produit, environnement en panne ou test flaky. Seuls les bugs produit deviennent des tickets.
  • Des échecs analysés jusqu'à iOS, Android et Flutter. Par exemple : un bouton visible que le test ne pouvait pas taper, une tab bar absente de l'arbre d'accessibilité iOS, la barre de navigation Android qui interceptait les taps. Pour chacun, j'ai trouvé la cause dans le comportement de la plateforme ou de Flutter, et corrigé le framework plutôt que de contourner dans les tests.
  • Un outillage partagé avec la squad. Un test plan par feature, une suite de tests de release, et des skills Claude Code qui génèrent les page objects à partir des maquettes Figma et des tickets Jira.

Moderniser un framework existant

  • Modernisation du framework. Migrations de Java et du client Appium, code mort retiré, logs réécrits pour se lire scénario par scénario. Le framework fait aujourd'hui la moitié de sa taille d'origine.

  • Une couverture élargie. Features derrière un feature flag, builds store, distributions TestFlight et Firebase, et webviews derrière le WAF de l'entreprise.
  • Un second framework en TypeScript. Construit de zéro, multi-plateforme et multi-locale, avec une comparaison documentée face à la stack Java.
