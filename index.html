QA Automation Mobile — BETCLIC Mars 2026 - Aujourd'hui (Freelance)

Betclic reconstruit son app mobile iOS et Android. J'y automatise les tests de la gamification des paris (défis, missions, classements, jeux de récompense), dans un repo de tests partagé entre le mobile et le web.

Construire l'automatisation en même temps que l'app

À mon arrivée, l'app n'existait pas encore vraiment et aucun test ne pouvait s'appuyer dessus. Le défi : être testable dès la première feature livrée, sans ralentir les devs.

  • Des test IDs posés directement dans le code de l'app. Sur mobile, un locator qui repère un écran par son texte casse à la première traduction ou au premier changement de maquette. Plutôt que d'attendre les devs, j'ai obtenu de poser moi-même les semantics dans le code Flutter, selon des règles écrites avec les tech leads. Les mêmes locators servent sur iOS et Android, et ils survivent aux refontes d'écran.
  • Les animations interactives, jusque-là impossibles à tester. Elles sont produites par l'équipe motion design dans un outil dédié, et l'app ne voyait rien de ce qu'il y avait dedans. J'ai écrit un outil qui injecte les test IDs directement dans les fichiers d'animation, vérifié le résultat avec le runtime Flutter, puis produit une version que le designer ouvre dans son propre logiciel pour comprendre la manipulation et la refaire lui-même.
  • Des données de test créées par API, pas à la main. Tester une mission de paris demande de vrais paris, placés puis réglés. Je les seed par API avant chaque scénario, à l'image des campagnes de production, sur un compte de test dédié. Le test ne passe par l'UI que pour ce qu'il vérifie vraiment : il est court, et il ne casse pas parce qu'un autre test a touché aux mêmes données.
  • Une nightly sur cinq marchés réglementés. Chaque pays a ses règles, ses contenus et ses comptes. La nightly tourne sur chacun d'eux ; le matin, je triage les échecs en trois cas : bug produit, environnement en panne, test flaky. C'est ce triage qui fait qu'un test rouge est pris au sérieux par l'équipe.
  • Remonter jusqu'au moteur mobile quand un test échoue sans raison. Un bouton visible que le test ne pouvait pas taper, une tab bar qui disparaissait de l'arbre d'accessibilité iOS, la navbar système Android qui absorbait les taps : à chaque fois j'ai isolé la cause dans le comportement d'iOS, d'Android ou de Flutter, et corrigé dans le framework plutôt que de contourner dans les tests.
  • Une méthode que la squad réutilise. Un test plan par feature, une suite de tests de release, et des skills Claude Code partagés qui génèrent les page objects à partir des maquettes Figma et des tickets Jira.

QA Automation Architect — ACCOR (CAC40) Nov. 2024 - Mars 2026 (Freelance)

Accor teste ses apps mobiles ALL (fidélité, réservation, séjour) avec un framework de tests automatisés qui avait quatre ans et plus personne pour le faire évoluer. Arrivé pour exécuter et maintenir des tests, j'en suis devenu le référent technique.

Remettre un framework legacy à l'état de l'art, puis aller plus loin

Le défi : moderniser un outil dont dépendaient toutes les équipes, sans jamais interrompre les runs.

  • Moderniser le framework sans arrêter les tests. Migration de Java et du client Appium par étapes, chacune validée par un run complet avant la suivante. J'en ai profité pour retirer le code mort et refaire les logs, lisibles scénario par scénario. Le framework a perdu la moitié de son poids et il est devenu le repo de référence de l'équipe.
  • Un device différent pour chaque scénario. Les tests tournaient tous sur le même modèle de téléphone, et les bugs propres à un modèle, à une tablette ou à un écran en paysage passaient inaperçus. J'ai fait distribuer chaque scénario sur un device différent de la device farm BrowserStack, avec un cache des apps et des devices pour ne pas payer l'initialisation à chaque session. Les échecs sont devenus reproductibles et les sessions plus rapides.
  • Un pipeline qui décide tout seul. Il dépendait d'un template externe et n'avait aucune quality gate. Je l'ai rendu autonome, avec un seuil de réussite en dessous duquel il casse, les résultats envoyés dans Xray et Jira, et une alerte Slack par périmètre. Trois minutes gagnées par run au passage.
  • Atteindre ce que les tests ne pouvaient pas atteindre. Les features derrière un feature flag, dont l'entrée du Travel Concierge, les builds store, les distributions TestFlight et Firebase, les webviews derrière le WAF de l'entreprise : j'ai ouvert chacun de ces accès aux tests, avec la méthode propre à chacun.
  • Des bugs de l'app diagnostiqués pour les devs. Le login iOS faisait échouer un run sur cinq. J'ai comparé des sessions qui passaient et des sessions qui échouaient sur le même build, isolé la cause, et travaillé le fix en binôme avec le tech lead iOS. Même approche pour les sessions expirées et les écrans de consentement absents.
  • Un second framework, en TypeScript, conçu de zéro. Pour le comparer à la stack Java, j'ai construit un framework où chaque scénario a sa propre session et sa propre fresh install, où les devices tournent entre les workers sans collision, et où la locale et la timezone de chaque test se lisent dans ses tags.
  • Une passation complète. Documentation, relais assuré jusqu'au dernier jour, et quelques fixes encore poussés après mon départ.
